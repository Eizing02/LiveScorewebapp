# Local operations and controlled integration

Automatic Worker live API calls remain disabled. An explicitly authorized local API-Sports probe now verifies the date endpoint and stages a read-only real schedule cache, separately from mock prediction pages. See API_CONNECTION_TH.md for actual account/filter limitations and request counts. Public API reads D1 only; transport injection tests do not contact the provider.

Provider client has one fixed HTTPS host and validated date or league/season fixtures queries, 10-second timeout, zero automatic retries, one filtered query per sync job, response size/schema checks and cache. It does not send a page parameter to /fixtures. A stale cache is returned only with stale=true. Provider remaining can tighten the ledger. Atomic D1 quota reservation enforces normal soft cap 65, results reserve up to 95 and last-five-call contingency unused automatically. Global 12.1-second spacing is conservative relative to five/minute and also covers window boundaries. Timeouts consume reserved budget because provider billing is uncertain.

Live activation requires API_FOOTBALL_KEY Worker secret, LIVE_API_ENABLED=true, INTEGRATION_APPROVED=true, PROVIDER_WINDOW_VERIFIED=true and a verified reset hour. Do not set them until the user authorizes a small integration test. Confirm direct vs RapidAPI, current-season permission/league coverage, reset timezone, minute limit headers, pagination and retention/redistribution rights. Initial plan is one EPL fixtures page: one expected billable request; confirm whether a separate account-status request is exempt before including it. Do not promise that the free plan has the current season.

No default admin password or service secret. For local signed calls create long random INTERNAL_SYNC_SECRET and ML_IMPORT_SECRET in ignored .dev.vars. HMAC covers method, path/query, millisecond timestamp, nonce and exact body. Expiry is five minutes, nonces are unique and body capped at 100 KB. Public origins do not receive private credentials. Put actual secrets in Worker/GitHub secret stores only.

The Python service_client is dry-run unless --execute is supplied. It never logs credentials. An active ML model is currently null. Batch model imports require an approved server-side model version, matching feature hash/cutoff, future scheduled fixture and pre-kickoff generation. Arbitrary candidate results cannot enter production.

Local D1 promotion/rollback endpoints require signed admin requests and approved:true. Candidate rows cannot be promoted until an operator imports verified eligibility. Python registry supports checksum verification and explicit --approve for local promote/rollback; neither was invoked in this development run. Registry keeps previous pointer; old immutable model directories are retained. Release bundles contain all models, schema/config/metrics/metadata and checksums; retain them in Git/private GitHub Releases. Actions artifacts are review copies with expiration, never the sole permanent store. Configure required reviewers on model-release before enabling release workflow.

No cron is configured in wrangler.jsonc. After separate preview/live approval, a possible schedule is 2–4 UTC runs/day; latency is best effort, not precise T-1h. Jobs use leased locks, dedup IDs, bounded batches, no infinite retry and last-good cache. Snapshot locking/evaluation runs on sync; delayed locking still cannot alter previously inserted prediction probabilities. DB triggers reject updates/deletes of locked rows and post-kickoff insertion. Corrections to actual results need evaluation revision/audit handling before live use.

Before Cloudflare: verify free plans, hard spend limits, D1 retention/storage, 10 ms real CPU, query/write metrics, provider mapping, fresh features, admin throttling and nonce retention cleanup. Current feature state and example fixtures are intentionally stale/mock; they must not be presented as current real predictions. Current mock sync covers one provider page; paging continuation, season rollover, coverage sync, live feature rebuilding and result correction revisions are explicit rollout work.

Cron and GitHub Actions can run while the personal PC is off only after a separately approved deployment and workflow setup. Nothing currently runs in the cloud. All automation is disabled by repository variable/default flags.

Feature history is archived by D1 triggers into immutable feature_snapshots on insert/update. Predictions must reference an archived feature hash for the same fixture/cutoff. Replacing the current features cannot erase the old evidence. Both snapshot deletion and hash reuse with different payload are rejected in integration tests.
