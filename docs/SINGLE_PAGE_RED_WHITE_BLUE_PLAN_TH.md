## 1. เป้าหมาย

ให้เปิดแล้วดูโปรแกรม ค้นหาคู่ เปิดบทวิเคราะห์ ดูคู่เด่น และติดตามผลได้จากหน้าทำงานเดียว บนคอมเห็นรายการและคู่ที่เลือกพร้อมกัน บนมือถือสลับแผงรายการกับรายละเอียดภายในจอหลักเดียว คืนตัวกรองและตำแหน่งเดิมเมื่อกลับ

เน้นหน้าตาแบบโปรแกรมบอล: วันที่ รายการแข่งขัน เวลา ทีม โลโก้ สกอร์ และสถานะ มาก่อนข้อมูลวิจัย ใช้ขาว–ฟ้า–แดงตามที่ผู้ใช้กำหนด ลดการเลื่อนหน้าหลักด้วยแผงข้อมูลและแท็บตามงาน ส่วนรายการหลายร้อยคู่ใช้ค้นหา กรอง และแบ่งหน้า

ขอบเขตยังเป็น React/TypeScript + Workers/D1 + Python ใน `D:\Football Prediction AI` ไม่แตะ `D:\Live score Project` ไม่เปิดบริการเสียเงิน และไม่อนุมัติโมเดลหรือ deploy ในงานออกแบบนี้

## 3. โครงสร้างหน้าทำงานเดียว

### Desktop ตั้งแต่ประมาณ 1280px

ใช้สามส่วนในหน้าต่างเดียว:

1. **รายการแข่งขันด้านซ้าย** กว้างประมาณ 180–220px มีรายการทั้งหมด ลีกติดตาม ประเทศ/รายการ และจำนวนคู่จากข้อมูลจริง
2. **โปรแกรมตรงกลาง** กว้างยืดหยุ่น เรียงเป็นแถวกระชับ แยกลีก มีเวลา ทีม โลโก้ สกอร์ สถานะ และตัวเลือกติดตาม
3. **วิเคราะห์คู่ด้านขวา** กว้างประมาณ 360–440px เปลี่ยนตามคู่ที่เลือกทันที รายการตรงกลางยังอยู่ตำแหน่งเดิม

ส่วนหัวมีชื่อระบบ วันที่/รอบ วันนี้–พรุ่งนี้ ค้นหาทีม และตัวกรอง ไม่วาง hero หรือสถิติวิจัยก่อนโปรแกรม ระบุเวลาบันทึกครั้งเดียวแบบกระชับ

มีตัวสลับงาน **โปรแกรม / คู่เด่น / ผลการทำนาย** อยู่ภายใน workspace เดียว การสลับเปลี่ยนชุดรายการตรงกลาง ไม่โหลดหน้าใหม่และไม่ล้างบริบทโดยไม่จำเป็น งานวิจัยและรายละเอียดระบบอยู่เมนูรอง

บนจอสูงเพียงพอ หัวและตัวกรองอยู่กับที่ เลื่อนเฉพาะกรอบรายการหรือกรอบข้อมูลที่ต้องอ่าน ไม่ให้รายละเอียดที่ยาวดันรายการคู่ลงทั้งหน้า เมื่อจอเตี้ยหรือขยายตัวอักษรมาก ให้ปรับเป็นรูปแบบที่อ่านได้ ไม่บังคับซ่อนเนื้อหาเพื่อรักษาความสูงจอ

### Tablet ประมาณ 768–1279px

เหลือสองส่วน: รายการคู่กับรายละเอียด ย้ายรายการลีก/ประเทศเป็นตัวกรองที่เปิดได้ ช่องค้นหายังเข้าถึงง่าย ไม่บีบสามคอลัมน์จนอ่านชื่อทีมไม่ออก

### Mobile ต่ำกว่าประมาณ 768px

เปิดมาพบวันที่และรายการคู่ทันที แตะคู่เพื่อแทนพื้นที่รายการด้วยแผงวิเคราะห์ในจอหลักเดิม มีหัวทีมและปุ่มกลับที่คืนตำแหน่งรายการ ตัวกรอง และคู่ที่เลือก ไม่ขยายรายละเอียดทั้งหมดแทรกใต้ทุกคู่

ปุ่มวันที่/ตัวกรองกระชับ ใช้แท็บข้อมูลในแผงวิเคราะห์ แสดงชื่อเต็มได้โดยไม่ลดฟอนต์ให้เล็ก ไม่มีการเลื่อนแนวนอนเพื่อหาสกอร์หรือปุ่มหลัก ใช้ safe area และความสูง viewport ที่เปลี่ยนตามแถบเบราว์เซอร์

## 4. รูปแบบแถวโปรแกรม

Desktop เรียง เวลา | เจ้าบ้าน+โลโก้ | สกอร์/เวลาแข่ง | ทีมเยือน+โลโก้ | สถานะ/ติดตาม โดยใช้ความสูงปกติประมาณ 48–60px และยืดเมื่อชื่อยาว มือถือจัดทีมและสกอร์ในแถวเดียวกันที่อ่านได้ อาจใช้ชื่อทีมสองบรรทัด

- แยกลีกด้วยหัวชื่อ โลโก้ ประเทศ และจำนวนคู่ พับ/ขยายได้
- ใช้ provider competition ID แยกลีก ไม่ใช้ชื่ออย่างเดียว เช่น Premier League ต่างประเทศหรือรายการชื่อ Cup ต้องไม่ปะปน
- สกอร์แสดงตามข้อมูลจริง คู่อยู่ระหว่างแข่งใช้สถานะพร้อมเวลาบันทึก หากไม่มีสกอร์คงสถานะไม่ทราบ ไม่ใส่ 0–0
- หลังเที่ยงคืนระบุวันที่ถัดไปหรือ +1 ให้รู้ว่าอยู่รอบเดิม เตะตรง 06:00 เข้ารอบใหม่
- ใช้วันรูปแบบเดียวกันตลอด UI โดยเก็บ ISO ภายในและแสดงวันที่ไทยที่มีปีสอดคล้องกัน
- มีตัวกรอง ทั้งหมด / รอแข่ง / ระหว่างแข่งที่บันทึก / จบ / เลื่อน–ยกเลิก
- มีช่องดูรายการทั้งหมดให้ชัดเจน ไม่มี allowlist ห้าลีกซ่อนตัวเลือกอื่น
- มีตัวเลือกลีกติดตามเพื่อช่วยใช้งานประจำวัน แต่สลับกลับทั้งหมดและเห็นจำนวนอื่นได้เสมอ

เริ่มแบ่งหน้าประมาณ 20–25 คู่ต่อคำตอบ API พร้อมตัวนับกรองจริง ไม่จำเป็นต้องสร้าง DOM หลายร้อยแถวพร้อมกัน หากข้อมูลมากขึ้นจึงพิจารณา virtual list จากผลวัด ไม่เพิ่ม dependency ก่อนจำเป็น

## 5. แผงวิเคราะห์แบบอ่านสั้นตามงาน

หัวแผงมีชื่อทีม/โลโก้ รายการ เวลาเตะ สกอร์ที่บันทึก และสถานะข้อมูล จากนั้นใช้สี่แท็บ:

| แท็บ | เนื้อหาที่ควรเห็น |
|---|---|
| สรุป | ความน่าจะเป็น 1X2 ของเรา ประตูคาดหมาย สกอร์เด่น เหตุผลสั้น และความพร้อมของคำทำนาย |
| ฟอร์ม–H2H | ล่าสุด 5/10/20 นัด เฉพาะเหย้า–เยือน ผลพบกัน ลีกเดียวกัน/ทุกถ้วย จำนวนตัวอย่างและค่าเฉลี่ย |
| ประตู | สูง–ต่ำตามเส้น BTTS และสกอร์ที่เป็นไปได้ โดยไม่แสดงทุกตลาดกางยาวพร้อมกัน |
| ข้อมูลทีม | ผู้เล่นขาด lineup และข้อมูลจาก API ที่มีจริง รวม forecast ผู้ให้บริการที่ติดป้ายแยกจากโมเดลเรา |

ข้อมูลรุ่นโมเดล cutoff แหล่งข้อมูล coverage และเวลาที่รับ เปิดอ่านเฉพาะเมื่อกดดู ไม่วางข้อความทางเทคนิคหลายย่อหน้าบังโปรแกรม

แยกสถานะให้ชัด: มีโปรแกรม / มีประวัติ / มีคำทำนายที่บันทึกก่อนเตะ / รอจับคู่ทีม / โมเดลยังไม่รองรับรายการ / เกมเริ่มแล้วไม่มีคำทำนายก่อนเกม แสดงเฉพาะส่วนที่มีจริง ข้อมูลขาดไม่ทำให้ทั้งแผงกลายเป็นหน้า error

เมื่อยังไม่เลือกคู่ ให้มีคำแนะนำสั้น “เลือกคู่เพื่อดูวิเคราะห์” เมื่อเปลี่ยนคู่เร็ว ต้องยกเลิกคำขอเก่าและไม่แสดงชื่อทีมใหม่คู่กับบทวิเคราะห์เก่า

## 6. ธีมขาว–ฟ้า–แดง

เปลี่ยนทิศทางเดิมสีเขียวเข้มตามคำขอใหม่ของผู้ใช้ โดยรักษาชื่อระบบ โลโก้จริง และข้อเท็จจริง

| บทบาท | สีที่เสนอ | จุดใช้งาน |
|---|---|---|
| พื้นหลัก | ขาว `#FFFFFF` | รายการและแผงวิเคราะห์ |
| พื้นรอง | ฟ้าอ่อนอมเทา `#F4F7FB` | พื้น workspace และหัวกลุ่ม |
| สีหลัก | น้ำเงิน/ฟ้าเข้ม `#1D4ED8` | แถบหัว เมนู ปุ่ม และคู่ที่เลือก |
| สีช่วยแบ่งส่วน | ฟ้าอ่อน `#EFF6FF` | แถวที่เลือกและพื้นที่สรุป |
| สีเน้น | แดง `#B42318` | สถานะสำคัญ เช่น ระหว่างแข่งที่บันทึก การยกเลิก หรือข้อผิดพลาด พร้อมข้อความ |
| เนื้อหา | เข้ม `#101828` | ชื่อทีม สกอร์ ตัวเลข |
| เนื้อหารอง | เทาเข้ม `#475467` | รายการ เวลา และคำอธิบาย |

สีฟ้าสด/อ่อนใช้เป็นพื้นหรือเส้น ไม่ใช้กับข้อความเล็กที่ contrast ไม่พอ แดงใช้พออ่านสถานะได้ ไม่ทาทุกสกอร์เป็นแดงหรือทำหน้าเหมือนแจ้ง error ตลอดเวลา ค่าจริงต้องตรวจ contrast ของคู่สีรวม border, focus, selected และ disabled ตอนพัฒนา

ใช้ IBM Plex Sans Thai ที่มีอยู่ต่อ ชื่อทีม/ข้อมูลหลักประมาณ 15–16px, controls 14–16px, supporting text 13–14px ปุ่มสัมผัสอย่างน้อย 44px ใช้ตัวเลข tabular และ SVG ชุดเดียว ไม่สร้างโลโก้ทางการขึ้นเอง

## 7. ขยายโปรแกรมโดยไม่บังคับขยายโมเดลพร้อมกัน

### ชั้นโปรแกรม

เพิ่ม catalog โปรแกรมที่รับการแข่งขันจาก response ตามวันที่ได้กว้างขึ้น เก็บ provider fixture/team/competition IDs ชื่อ ประเทศ ประเภทรายการ ฤดูกาล เวลา สถานะ สกอร์ nullable โลโก้ และ provenance ใช้ได้แม้ยังไม่มี canonical identity สำหรับ training

แยกการแข่งขันชาย/หญิง เยาวชน ทีมสำรอง และรายการระดับต่าง ๆ ตาม metadata ที่ยืนยันได้ หากไม่มีข้อมูลประเภทให้เป็นไม่ทราบ ไม่เดาจากชื่อจนเอาทีมคนละชุดมารวมกัน

เก็บ observations/current head สำหรับการแก้วัน เลื่อน หรือแก้สกอร์ โดยรักษาร่องรอยข้อมูลเดิม ข้อมูลที่เวลา/identity ด้านโปรแกรมผิดจริงต้องกักตามเหตุผล ไม่แต่งเติม

### ชั้นประวัติและคำทำนาย

ใช้ mapping และ gates ของโมเดลเดิมต่อ การเพิ่ม fixture ของบอลถ้วยหรือลีกใหม่ไม่ทำให้โมเดลที่ฝึกกับลีกเดิมเหมาะสมกับรายการนั้นโดยอัตโนมัติ ถ้ายังไม่ผ่านให้ดูโปรแกรมและข้อมูลที่มีได้ พร้อมป้ายว่ารอวิเคราะห์

รักษา cutoff ก่อน kickoff การล็อก prediction และการประเมิน 90 นาที ไม่เปลี่ยน weights/threshold เพื่อให้หน้าเว็บมีตัวเลขครบ ไม่สร้างย้อนหลัง ไม่รับรอง 70–80% จากการเปลี่ยน UI

คู่เด่นและชุด 3/5 ยังใช้เฉพาะคำทำนายที่ผ่านเงื่อนไขจริง ไม่เติมจากคู่ที่ไม่มีโมเดลเพื่อให้ครบจำนวน

## 8. API โควตาและภาพ

เริ่มเปิดคู่เพิ่มเติมจาก raw cache ที่มีอยู่ได้โดยไม่ต้องเรียก API-Football เพิ่ม การเพิ่มรายการจาก response รายวันเดิมไม่จำเป็นต้องเพิ่ม request แยกทุกลีก จำนวนและ paging ต้องตรวจจริงในการ sync ครั้งถัดไป

หน้าจออ่าน API ของระบบเราและแคชเท่านั้น วันที่ ลีก ค้นหา หรือเปิดรายคู่ไม่สร้าง provider request ไม่จำกัด การ sync และ enrichment ผ่าน broker/queue เดิม

ไม่ดึง injuries/lineups/predictions แยกครบ 332 คู่ เพราะกินโควตาสูงกว่าแค่โปรแกรมมาก ให้ใช้ข้อมูลที่มีอยู่ก่อน และเลือกเก็บเพิ่มเฉพาะคู่ที่ติดตาม/มีโมเดลรองรับตามงบที่ตั้งไว้ ตรวจสิทธิ์วันและ endpoint ตามบัญชีจริงเมื่อลงมือในส่วนนั้น

โลโก้จำนวนมากใช้โหลดตามรายการที่เห็นและเก็บ cache ตาม provider IDs ไม่ดาวน์โหลดทุกทีมทั่วโลกก่อนเปิดหน้า ไม่ใส่ภาพเป็น blob ใน D1 ไม่เปิด arbitrary image proxy และคง fallback เมื่อภาพเสีย

## 10. เกณฑ์รับงาน

- หน้าหลักมีรายการหรือ empty/error ที่อธิบายได้ใน viewport แรก ไม่มี hero ดันคู่ลงไป
- จอ 1366×768 และ 1440×900 เห็นโปรแกรมกับรายละเอียดพร้อมกัน หัว/ตัวกรองไม่เลื่อนหายตามบทวิเคราะห์
- จอ 320/390/430px ไม่มี body horizontal overflow แถวคู่แสดงทีม สกอร์/เวลา และทางเข้าวิเคราะห์ได้โดยไม่ปัดหาปุ่ม
- จอ 768/1024px ใช้สองแผงเมื่อมีที่เพียงพอ ไม่บีบชื่อทีมจนอ่านไม่ได้
- เนื้อหาไม่ถูกตัดเมื่อแป้นพิมพ์มือถือเปิด จอเตี้ย หรือขยายตัวอักษร 200%; เลื่อนอ่านได้เมื่อจำเป็น
- การเลือกคู่ไม่ล้างวันที่ ลีก คำค้นหา สถานะ หน้ารายการ หรือตำแหน่งที่อ่าน Back คืน focus และ state
- แท็บ/แผงใช้ keyboard และมีชื่อ accessible, focus, loading/error/retry และ reduced motion
- จำนวนแถว ตัวยอด และตัวกรองตรงกับข้อมูลที่ API ส่งจริง ค้นหา/กรองข้ามหน้าได้ ไม่กรองแค่ 20 คู่ที่โหลดมา
- ตัวอย่าง 332/3/329 ต้องทำซ้ำจาก snapshot ที่ระบุได้ แต่ไม่ hardcode เป็นยอดในระบบ
- 06:00 boundary, เวลาไทย, duplicate, missing score, postponed/cancelled และการเปลี่ยนเวลา ต้องไม่ผิด
- เพิ่มรายการโปรแกรมได้โดยไม่เปิด provider calls จาก browser ไม่เพิ่ม secret ใน bundle และไม่เปลี่ยน frozen model/auto-promote

## 11. ข้อเสนอที่ใช้เป็นค่าเริ่มต้นของแผน

ใช้โครงสร้างสามส่วนบน desktop และสลับแผงบนมือถือ เปิดให้ดูรายการทั้งหมดที่มีข้อมูล มีลีกติดตามเป็นตัวช่วย ธีมขาวเป็นพื้น ฟ้าเป็นสีหลัก แดงเน้นสถานะ โปรแกรมใหม่ไม่ต้องรอโมเดล แต่คำทำนายต้องผ่าน gates เดิมเสมอ

รอบนี้จบที่แผนและผลตรวจแคช ยังไม่ได้แก้หน้าจอหรือย้ายข้อมูลเข้า catalog ใหม่ และยังไม่เรียก provider เพิ่ม
